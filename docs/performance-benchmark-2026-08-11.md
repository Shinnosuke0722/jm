# jm 与竞品性能对比报告（Windows）

测试时间：2026-08-10 至 2026-08-11（Asia/Shanghai）<br>
被测提交：`5ccc0108ced112915323c3ca6b20d483321b042a`<br>
结论适用范围：本机 Windows x64、下述版本和测试场景；不能直接外推到 Linux、macOS 或其他版本。

## 1. 结论摘要

`jm` 在本地高频路径上确实明显更快、更省内存，但不能概括成“所有场景都领先”。

- `--version`：`jm` 中位数 **27.721 ms**，比本轮最快竞品 mise 的 48.415 ms 低 **42.7%**（约 **1.75×** 快）。
- `--help` / 非法命令：`jm` 比各自最快竞品低 **38.8% / 37.9%**。
- 本地 JDK 列表：0、10、100、1000 个安装项时，`jm` 比各规模下最快竞品分别低 **46.5%、46.2%、44.6%、30.1%**。
- 启动峰值工作集：`jm --version` 为 **6.52 MiB**，比内存最低竞品 jabba 的 7.70 MiB 低 **15.3%**；比 mise 的 13.59 MiB 低 **52.0%**。
- 二进制体积：`jm` 为 **3.97 MiB**，比第二小的 jabba 低 **46.6%**。
- 8 进程并发列出 100 个 JDK：`jm` 达到 **83.17 commands/s**，比第二名 jabba 高 **12.1%**。
- 冷缓存公网查询不是 `jm` 的领先项：`jm` 中位数 **1.084 s**，比 javm 的 0.942 s 慢 **15.1%**，但快于 mise 和 jabba。此项受上游 API、CDN 和返回量影响，不适合作为核心宣传数字。
- “内存更低”不是绝对结论：列出 1000 个 JDK 时，`jm` 峰值工作集 **8.79 MiB**，高于 jabba 的 7.93 MiB，但仍低于 javm 和 mise。

建议对外使用的严谨表述是：

> 在本次 Windows x64 基准中，jm 的常用本地命令中位延迟通常比最快竞品低约 30%–46%；`--version` 峰值工作集比内存最低竞品低约 15%。

不要表述为“所有操作都快一倍”“内存始终最低”或“安装速度最快”。

## 4. 方法与统计口径

### 4.1 计时与内存

- 每个正式样本都创建一个全新的 CLI 进程。
- 计时范围是进程创建到退出，包含参数解析、读取配置/注册表、格式化和写入已重定向的 stdout/stderr。
- 使用 Windows `GetProcessMemoryInfo` 读取进程退出时可获得的 `PeakWorkingSetSize` 与 `PeakPagefileUsage`。
- 表中时间和内存使用中位数；同时保留 P95 用于观察抖动。
- 核心矩阵每个 case 先预热 5 次，正式样本按随机顺序交错运行，避免某个工具固定占据冷热机顺序。
- 公网查询每个工具使用全新隔离目录，5 次正式样本采用轮换顺序；因此测到的是冷缓存端到端时间。

### 4.2 样本量

| 场景 | 正式样本数 |
|---|---:|
| `--version` | 每工具 50 |
| `--help`、非法命令 | 每工具各 40 |
| 本地列表 0 / 10 个 | 每工具各 30 |
| 本地列表 100 个 | 每工具 20 |
| 本地列表 1000 个 | 每工具 10 |
| 当前版本、JDK home、shell init | 每工具各 30 |
| 项目解析每个深度 | 每工具 25 |
| javm 冷发现 1000 个 | 10 |
| 8 进程并发批次 | 每工具 12（每批 8 个命令） |
| 冷缓存公网查询 | 每工具 5 |

### 4.3 隔离与等价性

- `JM_HOME`、`JABBA_HOME`、`JAVM_HOME`、mise 的 data/config/cache/state 目录全部隔离。
- 本地列表使用等量的合成 JDK 目录；javm 的正常列表使用预热后的 24 小时发现缓存，并额外测试了删除缓存后的首次发现。
- 输出内容并不完全相同。例如 1000 项列表时，`jm` 中位 stdout 为 162,514 bytes，jabba 为 16,893、javm 为 25,027、mise 为 14,893；因此列表结果应理解为各工具默认用户体验的端到端成本，而不是单位字节吞吐率。
- mise 是通用多语言版本管理器，功能范围远大于专用 Java 管理器；本报告比较的是用户执行相近命令时的实际开销，不代表相同产品范围下的实现效率。

## 5. 核心结果

### 5.1 进程启动

中位耗时，单位 ms：

| jabba | 49.224 | 49.622 | 49.287 |
| javm | 49.527 | 49.697 | 50.638 |
| mise | 48.415 | 46.110 | 45.417 |

`--version` 峰值工作集，单位 MiB：

| 工具 | 中位数 | P95 |
|---|---:|---:|
| **jm** | **6.52** | **6.58** |

`jm` 的 P95 启动耗时为 30.662 ms；jabba、javm、mise 分别为 54.596、55.771、53.469 ms，领先不是由少数极快样本造成。

### 5.4 项目目录向上解析

只有 `jm` 和 mise 在此处执行可比的父目录向上查找。jabba 和 javm 的项目文件只在当前目录读取，因此仅列深度 0。

中位耗时，单位 ms：

| 子目录深度 | jm | mise | jm 低于 mise |
|---:|---:|---:|---:|
| 0 | **28.993** | 69.633 | 58.4% |
| 5 | **28.779** | 77.265 | 62.8% |

深度 100 会让本测试目录超过传统 Win32 路径长度限制，进程在启动前即失败，因此正式上限设为 50；这不是任一 CLI 的性能失败。

深度 0 时 jabba 为 50.893 ms，javm 为 61.070 ms，但它们没有执行向上遍历，不能用于深层目录排名。

## 6. 公网远程查询（观测项）

查询 Temurin Java 21，每轮使用全新工具 home/cache：

| 工具 | 样本 | 中位耗时 | P95 | 返回行数 | 返回 bytes |
|---|---:|---:|---:|---:|---:|
| **javm** | 5 | **942.303 ms** | 1,039.728 ms | 2 | 111 |
| jm | 5 | 1,084.221 ms | 1,132.997 ms | 5 | 509 |
| mise | 5 | 2,032.968 ms | 2,092.430 ms | 13 | 308 |
| jabba | 5 | 2,446.847 ms | 2,546.136 ms | 1 | 8 |

命令分别为：

- `jm list --remote --distribution temurin --major 21 --no-color`
- `jabba ls-remote 21 --latest major`
- `javm ls-remote 21 --distribution temurin --latest major`
- `mise ls-remote java@temurin-21`

该结果不能解释 CLI 本体性能：各工具请求的上游、缓存策略、响应内容和输出量不同，而且网络状态会随时间变化。它只能回答“本次机器上用户实际等到结果要多久”。

## 7. 安装测试：为何没有给出排名

本轮尝试了两种安装基准，但都没有形成可以诚实排名的完整样本：

1. **本地 HTTP、同一 32 MiB 合成 JDK ZIP**：jm 和 jabba可以使用；javm 明确拒绝非 HTTPS 下载。这是合理的安全策略差异，不应通过修改竞品二进制绕过。
2. **固定 Temurin 21.0.12 官方 Windows ZIP（205,069,442 bytes）**：三者使用同一 HTTPS 资产，计划为 1 次预热 + 3 次正式。运行至第二轮时，GitHub release CDN 对 jabba 出现 TLS handshake timeout，整组样本不完整。失败资产来自 [Adoptium 官方发布文件](https://github.com/adoptium/temurin21-binaries/releases/download/jdk-21.0.12%2B8/OpenJDK21U-jdk_x64_windows_hotspot_21.0.12_8.zip)。
3. **本地 HTTPS**：测试证书无法在全自动、无交互条件下让三种 TLS 栈一致信任。没有通过关闭证书校验或修改竞品来“制造”数字。

因此本报告不宣称 `jm` 的下载、校验、解压或安装速度快于竞品。要得到有效排名，应在 CI 或专用测试机上部署受三种客户端共同信任的 HTTPS 服务，固定带宽、延迟、证书链和归档，再执行至少 10 次轮换样本。安装时还应分别报告：元数据查询、首字节、下载、checksum、解压、注册和默认版本切换。

## 9. 为什么 jm 会快这么多

从数据看，优势主要来自“固定启动成本小”和“热路径直接”，而不是简单归因于 Rust：mise 同样是原生 Rust 程序，但范围、插件/后端和配置能力更广。

可以从结果支持以下判断：

1. **基础启动成本低**：`--version`、`--help`、非法命令和空列表都稳定在约 28–29 ms，说明大量优势在进入具体业务前已经形成。
2. **专用 Java 范围**：jm 不需要启动通用多语言后端、插件发现和更复杂的配置模型。与 mise 的深目录差距随深度扩大，也符合配置发现路径更轻的表现。
3. **注册表直读**：jm 的正常本地列表读取自己的安装注册表；javm 首次目录发现比缓存路径多约 78 ms，证明目录发现/校验是可观成本。
4. **小二进制和小工作集**：3.97 MiB 二进制、约 6.5 MiB 启动峰值工作集，通常意味着需要映射和初始化的代码/数据更少。
5. **格式化成本控制较好**：1000 项时 jm 输出约为 jabba 的 9.6 倍，但仍先完成；因此领先不只是“输出更少”。

这些是由测量现象支持的工程解释，不是逐函数的因果证明。若要精确分解，应补做 ETW/WPA 启动跟踪、CPU flamegraph、磁盘 I/O 和逐阶段内部埋点。

## 10. 测试过程中发现的兼容性与副作用

- jabba 0.15.0 的 `init` 会修改 Windows PowerShell profile；因此没有把它与只输出脚本的 `jm shell init powershell`、`mise activate pwsh`直接混排。测试产生的 profile 内容已删除，并确认测试前该 profile 不存在。
- javm `init pwsh` 会在临时目录生成脚本；测试时 TEMP/TMP 已隔离。
- 手工构造带 UTF-8 BOM 的 `registry.json` 会被 jm 1.0.2 拒绝。正式 fixture 改为无 BOM JSON 后运行；建议后续决定是明确记录该格式要求，还是让解析器容忍 BOM。
- jabba/javm 的链接式 fixture 在当前 Windows 权限下不能创建符号链接，因此使用真实目录；jm 的全局 current 使用目录 junction。
- 本地 HTTPS 尝试临时创建的 `localhost` 测试证书已从 `CurrentUser\My` 和 `CurrentUser\Root` 两处删除并复核不存在。

## 11. 覆盖范围与未覆盖项

本报告覆盖：进程启动、帮助/错误路径、本地列表扩展性、首次发现缓存、当前版本、JDK home、项目解析、shell init、并发、本地峰值内存、二进制体积和公网远程查询。

未形成有效排名的项目：安装/下载/解压。未测试：真实 JDK 启动性能（它属于 JDK 而非管理器）、长期驻留内存、Linux/macOS、杀毒软件开关差异、低配/高配机器、更新/卸载写操作、代理环境和离线失败恢复。

一次 `--version` 只能说明固定启动成本，不能替代上述完整矩阵。本轮结果也表明：`jm` 在启动上领先，但公网远程查询并非第一，1000 项列表的最低内存也不是第一。

## 12. 清理与可复核性
